# Логика работы и настройки

## Синхронизация этапа 2

Канонический Apps Script вызывает только `POST /api/tasks/sync`. Он передаёт стабильный UUID строки и контент, а Laravel авторизует индивидуальный токен, находит одну интеграцию и сам выбирает create/update/skip. Для skip выполняются нужные чтения каталога, но внешние POST/PUT не выполняются; подтверждённые hash, payload и дата не меняются.

Sheets владеет полным набором labels задачи: заданная severity отправляет одно имя из разрешённого каталога, пустая severity отправляет `labels: []` и очищает также вручную добавленные labels. Пустой ответственный отправляет `assignee_id: 0`; сервер принимает очистку только после подтверждения ActiveCollab, что назначение и labels совпадают с отправленными.

Для нового подключения администратор выдаёт отдельный токен через CLI `integrations:tokens issue`, затем задаёт его в Script Properties как `INTEGRATION_SERVICE_TOKEN`. Общий токен включается только временно для выбранных старых интеграций и выключается после обновления их скриптов. Перед установкой скрипта миграция UUID должна быть завершена и интеграция должна быть в UUID-режиме.

## Общий сценарий

1. Поднимаем Laravel-проект.
2. Логинимся в Orchid-админку.
3. Открываем раздел `Apps Script`.
4. При необходимости вставляем или редактируем код `activecollab_sync.gs`.
5. Скачиваем `activecollab_sync.gs`.
6. Вставляем его в Google Apps Script, привязанный к нужной таблице.
7. В Script Properties задаем:
   - `INTEGRATION_SERVICE_URL`
   - `INTEGRATION_SERVICE_TOKEN`
   Где брать:
   - `INTEGRATION_SERVICE_URL` — публичный базовый URL этого Laravel-сервиса без `/admin` и без `/api/...`
   - `INTEGRATION_SERVICE_TOKEN` — значение `GOOGLE_SHEETS_INTEGRATION_TOKEN` из `.env` или из переменных окружения сервера
8. Создаем интеграцию в админке.
9. Вставляем ссылку на Google Sheets или `spreadsheet_id`.
10. Заполняем параметры ActiveCollab. Для UUID-шаблона оставляем интеграцию неактивной и выполняем контролируемый перенос из [DEPLOY](DEPLOY.md#переход-на-uuid-шаг-14), включая пустой манифест для новой таблицы без истории. Затем включаем интеграцию.
11. После этого из таблицы можно создавать и обновлять задачи в ActiveCollab.

Важно для локального теста:

- `http://localhost` подходит только для открытия админки в браузере.
- Для реального вызова из Google Apps Script нужен публичный URL, например через `cloudflared` или `ngrok`.
- Именно этот URL и нужно указывать в `INTEGRATION_SERVICE_URL`.

## Что именно заполняется в интеграции

Нужно указать:

- `Название`
- `Google Sheets ID`
- `ActiveCollab API Base URL`
- `Project ID`
- `Активна`

Опционально:

- `Task List ID или название списка`
- `ActiveCollab API Token`

## Откуда брать значения

### Google Sheets ID

Берется из URL таблицы:

`https://docs.google.com/spreadsheets/d/{SPREADSHEET_ID}/edit`

Можно вставить полную ссылку, сервис сам выделит `spreadsheet_id`.

### ActiveCollab API Base URL

Для self-hosted ActiveCollab обычно это:

`https://your-activecollab.example.com/api/v1`

Если указать URL без `/api/v1`, сервис добавит суффикс автоматически.

То есть обычно:

- `ActiveCollab API Base URL = https://your-activecollab.example.com/api/v1`

Проверить можно так:

```bash
curl -I https://your-activecollab.example.com/api/v1
```

Если endpoint живой, это и есть нужная API base URL.

### Project ID

Обычно берется из URL проекта.

Пример:

`https://your-activecollab.example.com/projects/10`

Здесь:

`Project ID = 10`

Можно вставить не только число, но и полную ссылку на проект.

### Task List ID или название списка

Берется из ActiveCollab API или через вспомогательные endpoints Laravel.

Task List выбирается среди существующих списков выбранного connection и проекта. Пустой или неизвестный ID не приводит к выбору первого списка или созданию внешней сущности: сохранение отклоняется валидацией.

Можно получить через:

- `GET /api/integrations/activecollab/task-lists`

Либо напрямую из ActiveCollab API.

### ActiveCollab API Token

Берется в самом ActiveCollab для пользователя, у которого есть доступ к нужному проекту и задачам.

Если глобальный `ACTIVECOLLAB_API_TOKEN` уже задан в `.env`, поле токена в интеграции можно оставить пустым.

Этот токен:

- хранится в Laravel
- не должен храниться в Apps Script
- не должен вставляться в таблицу

## Что происходит после настройки

1. Пользователь выбирает строку в Google Sheets.
2. Нажимает `Синхронизировать задачу`.
3. Apps Script отправляет UUID и payload в Laravel с индивидуальным токеном.
4. Laravel находит интеграцию по token record и проверяет UUID-привязку.
5. Laravel создаёт, обновляет или пропускает запись в ActiveCollab.
6. Ссылка на задачу записывается обратно в таблицу.
7. История синхронизации сохраняется в базе.

## Важные замечания

- `activecollab_sync.gs` теперь канонически хранится в базе данных и редактируется через админку.
- Если файла `plugin/app/activecollab_sync.gs` нет на диске, это не проблема.
- Файл на диске нужен только как стартовый шаблон, если он существует.
- URL задач для браузера вычисляется из `ActiveCollab API Base URL`.
- Старый ключ скрипта `poc.gs` больше не используется; legacy-запись при миграции безопасно схлопывается в `activecollab_sync.gs`.


## Проверка привязки перед синхронизацией

`external_id` сохраняет формат `{spreadsheet_id}:{sheet_id}:{row_number}`. Перед create существующий экспорт проверяется на соответствие текущей интеграции и проекту. Запись с null integration ID или другим контекстом блокируется конфликтом; автоматически переносить её или создавать вместо неё новую задачу нельзя.

Наличие полной привязки (положительный task ID и непустой task URL) запрещает повторный create независимо от `status`. В частности, ошибка update переводит legacy-статус в `failed`, но сохраняет связь, последний успешный hash и подтверждённые source payload, отправленный payload и response. Последующий create возвращает прежний 409 с task ID/URL. Неполные привязки и `created/updated` без полной связи требуют ручной сверки и возвращают `legacy_binding_conflict` без HTTP.

Update ищет экспорт одновременно по integration ID, project ID, идентичности записи (UUID после перевода, legacy locator до него) и task ID. Если полной привязки нет, сервис возвращает 409 до построения payload и вызова ActiveCollab. Поиск по одному глобальному task ID и обновление без найденного экспорта исключены. Чужие task ID/URL в конфликте не раскрываются.

Шаг 1.2 добавляет короткую транзакцию reservation: уникальный экспорт + operation UUID + running attempt + lease. Конкурент получает 409, HTTP выполняется вне транзакции. Завершение допускается только владельцу running-операции с действующим lease, экспорт и attempt фиксируются атомарно. Истёкший lease становится unknown; поздний ответ не подтверждает успех и не перезаписывает другую операцию.

Ошибка маппинга до HTTP — failed, её можно повторить после исправления. Внешние ошибки после возможной отправки и сбой сохранения результата — unknown, автоматический повтор запрещён. Исторические pending/failed классифицируются unknown отдельным backfill либо тем же правилом при первом запросе. Новая история не придумывается для старых снимков.

Timeout подключения — 5 секунд, полный — 30, lease — 120; lease должен превышать полный timeout. Exactly-once между AC и локальной БД не обещается. UUID реализован на шаге 1.4; индивидуальные токены и новый sync API остаются следующим этапом. Административное восстановление реализовано на шаге 1.3.


## Административное восстановление

В истории экспортов администратор открывает «Проверить». Доступ требует одновременно полномочий управления users, roles и recovery; обычный токен интеграции их не заменяет. Экран показывает сохранённый источник и до 50 последних попыток. Выбор другой попытки меняет только preview, без внешнего HTTP и записи.

Для bind/verify сервер резервирует reconcile attempt и requested audit, затем вне транзакции получает задачу через GET в выбранном проекте. Перед фиксацией проверяет свежего actor и неизменность effective назначения, включая явно назначенное connection, сравниваемое только в памяти. Любое несовпадение, отзыв прав или stale operation запрещает решение. Один GET не подтверждает содержимое: старый hash инвалидируется; для новой цели очищается чужой confirmed snapshot, исторические attempts остаются.

Подтверждение отсутствия требует остановки старых mutating workers, внешней сверки и явного решения с причиной. Оно не отправляет create. Замена недоступной задачи запускается отдельно, использует выбранный источник и текущие маппинги; таймаут не разрешает повтор. Если legacy source неполон, после разрешения unknown отправить актуальные данные обычным Update из Sheets: remote_missing ответ сохранит source в failed attempt без HTTP, затем администратор сможет выбрать его для замены. При unresolved replacement такой Update не изменит operation ID.

Два действия одной записи конкурируют через export lock; запрос имеет UUID и expected state. Audit requested/result и состояние/attempt фиксируются атомарно, повтор формы не выполняет HTTP второй раз. Старые unknown attempts не переписываются в succeeded; successful reconcile — результат решения, а не подтверждение старой синхронизации.

Scheduler каждую минуту запускает integrations:expire-sync-operations. Просроченный running становится unknown, не новой попыткой. Missing attempt history выводится в report без реконструкции; dry-run ничего не пишет.


## UUID и перемещение строки (шаг 1.4)

UUID назначается в скрытой колонке `SheetCollab UUID` под document lock и сохраняется/flush до HTTP. UUID-интеграции используют только `(integration_id, record_uuid)`. Позиция в той же таблице может меняться; новый UUID на прежнем месте независим. Legacy и UUID режимы не смешиваются, переход выполняет административная CLI-команда с dry-run/audit при inactive и полной остановке редактирования.

Reserve сериализует короткий участок integration → export, не внешний HTTP. Accepted attempt обновляет текущий locator; rejected request и поздний callback не возвращают старую позицию. Unknown/remote_missing по-прежнему блокируют обычный повтор/автоматическую замену. Recovery исторического источника без UUID допускается только для того же export и не переписывает старые attempts.

Apps Script проверяет копии UUID во всей таблице; для копии пользователь явно выбирает новую запись со сбросом ссылки. Ответ ищет уникальный UUID заново, включая другой лист; при удалении/дубликате ничего не записывает в старый row. Сортировать нужно полную строку с технической колонкой. LockService не блокирует ручные правки Google UI: правка между последней проверкой и записью не имеет гарантии атомарности. Полный переход канонического скрипта из DB в Git остаётся отдельным этапом.
