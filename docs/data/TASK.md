# Техническое задание: безопасная синхронизация и упрощение SheetCollab

## 1. Цель и границы

Развивать SheetCollab как компактный многопользовательский Laravel-монолит для синхронизации задач из Google Sheets в ActiveCollab. Поддерживать несколько подключений ActiveCollab, несколько Google-таблиц и проектов, индивидуальные маппинги и разграничение доступа.

Сохранить Laravel, PHP, Orchid, MariaDB, Google Apps Script, DTO, безопасное формирование HTML, PHPUnit, PHPStan, Pint и Docker Compose. Обновление версий платформы и зависимостей включить в отдельный этап 7 (§13), с аудитом совместимости, обновлением lock-файлов и проверками. Не смешивать его с изменениями бизнес-логики этапов 1–6.

Направление синхронизации остаётся Google Sheets → ActiveCollab с возвратом ссылки и результата в таблицу. Обратная синхронизация содержимого и статусов из ActiveCollab не входит в задачу.

Результат: одно действие «Синхронизировать строку», стабильная идентификация записи, защита от повторного создания, история попыток, понятная настройка подключений и безопасная миграция существующих интеграций.

Этот документ задаёт общий объём работ. Перед реализацией каждого этапа подготовить конкретный `work/PLAN.md`, согласовать его и выполнить только согласованный этап. Создание этого ТЗ не означает разрешение на реализацию всех этапов.

## 2. Подтверждённое исходное состояние

Основание: локальные исходники репозитория и предоставленные пользователем рекомендации. Исторические результаты из `docs/CURRENT_STATE.md` не считать актуальным запуском проверок.

- В `routes/api.php` реализованы create, update и три справочника под `/api/integrations/activecollab`.
- `VerifyIntegrationToken` проверяет общий `GOOGLE_SHEETS_INTEGRATION_TOKEN`.
- `ActiveCollabTaskService::create()` запрещает повторное создание только для `created` и `updated`. Ошибка update переводит запись в `failed`, сохраняя возможность ошибочного повторного create.
- `ActiveCollabExportRepository::findByTaskId()` не ограничивает поиск интеграцией. Update может выполнить внешний запрос вообще без найденной записи экспорта.
- Проверка экспорта и создание `pending` выполняются отдельно; уникальный индекс сам по себе не резервирует единственного исполнителя внешнего запроса.
- `external_id` — уникальный глобальный ключ `{spreadsheet_id}:{sheet_id}:{row_number}`. Номер строки нестабилен.
- `sync_hash` — MD5 от 13 значений через `|`; пропуск неизменённого update отсутствует.
- `ActiveCollabRepository` — единственная точка HTTP-вызовов ActiveCollab; явные timeout и политика повторов не заданы. Ошибки логируют фрагмент тела внешнего ответа.
- `ActiveCollabIntegration` хранит URL и зашифрованный API token, проект, таблицу и маппинги; часть значений берётся из глобального config.
- Справочники API используют глобальное подключение. Сохранение настроек через `ActiveCollabIntegrationSettingsService` может создать Task List.
- Apps Script имеет отдельные действия create/update; `GoogleAppsScriptService` читает канонический скрипт из `script_assets`, заполняя его из файла при отсутствии записи.
- Orchid уже содержит пользователей и роли. Использовать существующий механизм ролей вместо создания второй системы.
- `work/diff.txt` пуст: дополнительный diff не предоставлен. Перед планированием проверить рабочее дерево и сохранить чужие изменения.

## 3. Архитектурные ограничения и решения

1. Контроллеры: валидация → DTO → сервис. Бизнес-логика остаётся в сервисах.
2. Все HTTP-вызовы ActiveCollab пока остаются в `app/Repositories/ActiveCollab/ActiveCollabRepository.php`. Он выполняет роль клиента; переименование в `ActiveCollabClient` не является целью само по себе.
3. Сохранить существующие имена `ActiveCollabIntegration` и `ActiveCollabTaskExport` и их таблицы. Не переименовывать их механически в Integration/TaskSync.
4. Добавить `record_uuid` как отдельную стабильную идентичность. Формат `external_id` не менять: оставить его legacy-локатором. После миграции убрать его роль глобального уникального ключа, сохранив индекс и совместимость старых запросов.
5. На первых этапах сохранить Repository-слой, особенно атомарную работу с экспортами. Удаление простого integration repository и переход к прямому Eloquent допустимы только отдельным согласованным шагом с обновлением ограничения «Repository pattern for all DB access» в `CLAUDE.md`.
6. Изменение роли `external_id`, схемы состояний и источника Apps Script должно сопровождаться обновлением противоречащих правил `CLAUDE.md`, `AGENTS.md` и `work/AGENT_RULES.md` там, где они присутствуют. До соответствующего этапа действуют текущие ограничения. Пользователь запросил эти целевые изменения, но не механическое удаление всех ограничений.
7. Не добавлять универсальную платформу интеграций, микросервисы, React/Vue, Redis/RabbitMQ, Kubernetes, сложную шину событий или поддержку Jira/GitHub Issues.

## 4. Целевая модель данных

Имена новых таблиц и полей ниже — требования к целевой схеме; точные имена новых миграций указать в плане этапа. Все изменения схемы проводить новыми миграциями, не редактируя выполненные миграции.

### 4.1. Подключение — ActiveCollabConnection

Новая таблица `active_collab_connections`:

- `id`: UUID, первичный ключ;
- `name`, `base_url`: обязательные строки; URL нормализован, без встроенных учётных данных;
- `api_token`: обязательный TEXT с Laravel encrypted cast, скрытый при сериализации;
- `active`: boolean; `created_at`, `updated_at`.

Одно подключение используется несколькими интеграциями и проектами. Изменение токена подключения доступно администратору; менеджеру не раскрывать общий секрет. Используемое подключение нельзя физически удалить: разрешить отключение.

### 4.2. Интеграция — ActiveCollabIntegration

В `active_collab_integrations` добавить `connection_id` с FK. Сохранить имя, `spreadsheet_id`, project ID, default task list, три JSON-маппинга и active.

На целевом этапе URL и AC token берутся только из connection. Старые поля удаляются после проверенной миграции и окончания совместимости.

Для первого релиза сохранить существующее правило: одна Google-таблица привязана к одной интеграции и одному проекту, несколько таблиц могут использовать одно connection. Fan-out одной таблицы в несколько проектов не реализовывать.

Смену connection/project у интеграции с привязанными задачами блокировать; для другого назначения создавать новую интеграцию с явным сценарием переноса. Это предотвращает обновление задач по совпадающим ID в чужом проекте.

### 4.3. Состояние строки — ActiveCollabTaskExport

Сохранить текущую таблицу и payload-поля. Добавить:

- `record_uuid`: UUID, сначала nullable; целевой уникальный ключ `(integration_id, record_uuid)`;
- `last_attempt_status`: `idle`, `running`, `succeeded`, `failed`, `unknown`;
- `binding_status`: `unbound`, `bound`, `remote_missing`;
- `operation_id`: nullable UUID текущей операции;
- `lease_expires_at`: nullable timestamp для обнаружения зависших операций;
- `synced_at`: nullable timestamp последней подтверждённой синхронизации;
- `hash_version`: nullable строка, позволяющая отличить legacy MD5 от нового SHA-256.

`task_id` и `task_url` описывают подтверждённую связь, а не успешность последней попытки. Ошибка обновления не обнуляет связь, последний успешный hash и подтверждённый payload. Историческое поле `status` сохранить для старого API/UI на переходный период; затем удалить только после перевода потребителей.

Номер строки — текущая позиция, `external_id` сохраняет прежний формат. Для поиска по task ID обязателен контекст интеграции, проекта и исходной записи; индекса `(integration_id, task_id)` достаточно, глобальную уникальность task ID не вводить.

Исторические экспорты с `integration_id = null` сохранить и вывести в отчёт миграции; не привязывать по догадке. Для новых экспортов интеграция обязательна. Удаление интеграции с историей блокировать, использовать деактивацию.

### 4.4. История попыток

Новая таблица `active_collab_sync_attempts` и модель `ActiveCollabSyncAttempt`:

- UUID `id`, `export_id`, `integration_id`, уникальный UUID `operation_id`;
- `action`: `create`, `update`, `skip`, `reconcile`;
- `status`: `running`, `succeeded`, `failed`, `unknown`;
- `started_at`, `finished_at`, nullable HTTP status и безопасный error code/message;
- очищенные source payload, отправленный payload, ответ и вычисленный hash при наличии.

Записывать каждую принятую попытку, включая skip и ошибки до отправки. Отклонённые неавторизованные запросы не записывать в историю чужой интеграции. Секреты и заголовки авторизации в историю не сохранять.

### 4.5. Доступ, токены и аудит

- `active_collab_integration_user`: `integration_id`, `user_id`, уникальная пара; роли пользователя хранить существующим механизмом Orchid.
- `active_collab_integration_tokens`: UUID, integration ID, имя, уникальный SHA-256 hash случайного токена, revoked/created/last-used timestamps. Исходный токен показывать только при выпуске; предусмотреть одновременное существование старого и нового токена для управляемой ротации.
- `admin_audit_logs`: UUID, actor ID, действие, тип/ID объекта, integration/connection context, timestamp, очищенные изменения. Не хранить исходные токены и их зашифрованные значения в before/after.
- FK и индексы вводить после проверки исторических данных; миграция не должна удалять осиротевшие записи молча.

## 5. Единый API-контракт

### 5.1. POST /api/tasks/sync

Авторизация: Bearer-токен конкретной активной интеграции. Интеграция определяется токеном; `spreadsheet_id` обязан совпадать с её таблицей. Нельзя переключить интеграцию подменой body.

JSON-запрос:

```json
{
  "record_uuid": "ae091ce2-282a-43ad-a258-85a2b8eecfc4",
  "spreadsheet_id": "google-spreadsheet-id",
  "sheet_id": "0",
  "row_number": 8,
  "environment": "stage",
  "section": "Каталог",
  "description": "Не открывается карточка товара",
  "severity": "critical",
  "priority": "высокий",
  "device": "desktop",
  "resolution": "1920x1080",
  "screenshot": "https://example.test/screenshot.png",
  "comment": "Воспроизводится стабильно",
  "task_type": "backend",
  "responsible": "QA",
  "reporter": "Автор",
  "status": "новая"
}
```

`record_uuid`, источник и три текущих обязательных бизнес-поля обязательны. Остальные бизнес-поля nullable, как в действующем API. `external_id`, action, connection и task ID определяет сервер. Валидация должна задавать разумные пределы длины строк и размеров запроса; конкретные значения зафиксировать в плане.

Успешный ответ сохраняет envelope `data`:

```json
{
  "data": {
    "record_uuid": "ae091ce2-282a-43ad-a258-85a2b8eecfc4",
    "action": "created",
    "task_id": 123,
    "task_url": "https://ac.example.test/projects/10/tasks/123",
    "synced_at": "2026-10-29T12:00:00Z",
    "sync_hash": "64 lowercase hex characters",
    "operation_id": "operation-uuid"
  }
}
```

- `201`: created; `200`: updated или skipped. При skip возвращать последнюю подтверждённую дату синхронизации, время попытки хранить отдельно.
- `401`: отсутствующий, отозванный или неверный токен.
- `403`: отключённая интеграция/connection или несовпадение таблицы с токеном.
- `422`: неверные данные или обязательный маппинг.
- `409`: операция уже выполняется, неоднозначная legacy-привязка, удалённая внешняя задача или неизвестный результат предыдущей операции.
- `502`: подтверждённая ошибка upstream; `504`: таймаут с явным признаком неопределённого результата, если он возможен.

Ошибки возвращать как `error: {code, message, operation_id, retryable}`; для validation также `errors`. Codes должны различать `sync_in_progress`, `legacy_binding_conflict`, `remote_task_missing`, `sync_outcome_unknown`, `mapping_invalid`, `upstream_error`. `retryable` разрешает только повтор, безопасный с учётом сохранённого состояния.

### 5.2. Справочники и административные операции

Предусмотреть авторизованные маршруты Orchid для проверки connection, списка проектов и справочников task lists/users/labels выбранного connection/project. И API-справочники, и UI должны использовать явный контекст, а не глобальный config. Конкретные внешние методы и форматы ответов проверить перед реализацией по поддерживаемому ActiveCollab API.

Повтор sync из истории доступен менеджеру разрешённой интеграции и администратору; использовать тот же сервис и те же блокировки. Перед отправкой показать, что повтор использует сохранённый source payload и текущие маппинги, которые могут отличаться от данных в Sheets. Для unknown повтор создания недоступен до разрешения неопределённости.

### 5.3. Совместимость

Существующие POST/PUT `/api/integrations/activecollab/tasks...` и их ответы сохранить как адаптеры на переходный период. Legacy create с уже существующей связью возвращает прежний `409` с task ID/URL независимо от ошибки последнего update. Legacy update проверяет соответствие task ID интеграции и записи до внешнего запроса; произвольное обновление без привязки запретить и документировать как исправление безопасности.

Новый sync принимает только индивидуальный токен. Глобальный токен разрешён временно только для явно включённых legacy-интеграций и старых маршрутов; список и использование контролировать. Для остальных старые маршруты должны принимать индивидуальный токен с теми же ограничениями доступа. После перехода всех таблиц отключить global token, затем удалить legacy-код отдельным релизом.

## 6. Надёжность и обработка ошибок

### 6.1. Идентификация и Apps Script

- Создать скрытую техническую колонку `SheetCollab UUID`; UUID назначать и сохранять до первого HTTP-запроса. Назначение защитить `LockService` и повторным чтением ячейки.
- Меню содержит одно основное действие «Синхронизировать строку».
- UUID сохраняется при сортировке полной строки, вставке и перемещении; инструкция должна требовать сортировку диапазона вместе с технической колонкой. Сортировку только части бизнес-колонок невозможно сделать безопасной одной скрытой колонкой — явно описать ограничение.
- Проверять повторяющиеся UUID при копировании строк. Дубликат блокирует отправку; для копии предусмотреть явное действие назначения нового UUID со сбросом локальной ссылки. Никогда не менять UUID исходной записи автоматически.
- В Script Properties оставить URL сервиса и индивидуальный токен; AC token не передавать.
- После ответа повторно найти строку по UUID и проверить её уникальность перед записью ссылки/ошибки: пользователь мог переместить строку во время HTTP-запроса.

### 6.2. Атомарность

Уникальная запись состояния и право выполнить внешний вызов резервируются транзакционно в MariaDB. Использовать insert с обработкой unique conflict и условный захват operation ID/lease. Проверка последнего hash и выбор действия выполняются после захвата, чтобы конкурентный запрос не использовал устаревшее состояние.

Внешний HTTP-вызов выполнять вне длинной DB-транзакции. Завершать операцию только условно по её operation ID, чтобы поздний ответ не перезаписал результат другого исполнителя. Для работающей операции второй запрос получает `409 sync_in_progress` без второго внешнего вызова.

Истёкший lease не доказывает, что ActiveCollab не выполнил create. Зависший create переводить в unknown; автоматическое повторное создание запрещено. Lease и HTTP timeout согласовать в плане этапа.

### 6.3. Неопределённый результат и восстановление

Явно задать connect timeout и total timeout; стартовые значения 5 и 30 секунд сделать системной конфигурацией. Не добавлять автоматические повторы create.

Различать ошибку до отправки, подтверждённый отказ, timeout/обрыв после возможной отправки и сбой сохранения результата после успешного внешнего create. Не считать любую 5xx или некорректный ответ доказательством отсутствия созданной задачи.

При unknown сохранить попытку, связь при её наличии и данные для reconciliation. Если AC не предоставляет проверенный idempotency/search-механизм, реализовать административное разрешение: привязать подтверждённую существующую задачу после проверки connection/project либо явно подтвердить отсутствие результата и разрешить новую попытку с аудитом. Не обещать exactly-once между БД и внешним API.

При внешнем 404 сохранить task ID и установить `remote_missing`; не создавать замену автоматически. Явное восстановление/создание замены — отдельное подтверждаемое действие с аудитом, доступное администратору.

При update unknown не выполнять hash-skip на основании неподтверждённой попытки; сначала разрешить её результат. Повторы GET допускаются ограниченно; повторы PUT — только после подтверждения безопасности поддерживаемой AC-операции. Ошибки и ответы очищать от секретов до логирования и сохранения.

### 6.4. Hash содержимого

Выделить построение конечного AC payload в `ActiveCollabTaskPayloadBuilder`, сохранив `ActiveCollabTaskBodyBuilder` и экранирование пользовательского HTML.

Вычислять SHA-256 от канонического JSON конечного payload и идентичности назначения (connection/project), с фиксированным порядком ключей и определённой обработкой null/отсутствующих полей. Включать результат маппингов и все реально отправляемые поля; не включать временные метки попытки. Ссылку на источник включать, если она входит в тело задачи.

Пропускать update только при совпадении нового hash с последним подтверждённым hash той же версии и отсутствии unresolved операции. Переход с MD5 допускает одно контролируемое обновление. Изменение маппинга должно вызывать update даже при неизменных полях строки.

Отдельно проверить снятие assignee/label: пропуск поля и очистка назначения могут иметь разную семантику. Реализовать и покрыть тестами поведение поддерживаемого AC API.

## 7. Настройки, безопасность и Orchid

### Настройки

- `.env`: APP_KEY, DB, общие системные параметры, timeout и временные legacy-флаги. Целевые URL/token/project/маппинги берутся только из connection/integration.
- Удалять fallback только после переноса эффективных значений и проверки полноты конфигурации.
- Сохранение формы не создаёт Task List. Получение справочников и «Проверить подключение» — явные операции без создания внешних сущностей.
- Task List выбирается из доступных; создание извне оставлять только отдельным явным действием, если оно будет включено в план.

| Роль | Разрешения |
| --- | --- |
| admin | Все connections, интеграции, пользователи, назначения доступа, секреты, ротация токенов, аудит и восстановление unknown |
| manager | Разрешённые интеграции: просмотр, настройка маппингов, история, безопасный повтор; без доступа к общим AC-секретам и управлению пользователями |
| viewer | Только просмотр разрешённых интеграций и истории, без изменения, повторов и выпуска токенов |

Связь пользователя с интеграцией обязательна для manager/viewer; admin имеет полный доступ. Менеджер может выбирать только уже разрешённый контекст connection через назначенную интеграцию. Новые connections, интеграции и назначения доступа создаёт admin.

Проверять доступ на сервере для экранов, actions, маршрутов скачивания, статистики, справочников и повторов; скрытого пункта меню недостаточно. Для чужого объекта возвращать 404 без метаданных. Аудировать настройки, доступы, ротации, деактивации и ручное восстановление. API token даёт право sync и чтения справочников своей интеграции, но не административного управления.

### Интерфейс

Основное меню: Dashboard, Connections, Integrations, Sync History, Users. Роли доступны внутри управления пользователями; доступность пунктов зависит от прав.

Мастер интеграции для admin: Google Sheets URL → connection (выбрать или создать) → проект → default list и маппинги → проверка подключения → выпуск индивидуального токена и инструкция Apps Script.

В карточке интеграции: состояние connection, справочники, настройки, инструкция, скачивание скрипта и история. Dashboard и журнал фильтруются правами пользователя; журнал различает связь с задачей и результат попытки, показывает unknown/running/remote_missing.

### Единственный источник Apps Script

Канонический исходник — `resources/apps-script/activecollab_sync.gs` в Git. Скачивание отдаёт файл текущего деплоя, без зависимости от доступности GitHub.

Перед отключением DB-редактора экспортировать все `script_assets` и сравнить с файлом; полезные изменения перенести через review, расхождения не перезаписывать молча. Убрать editor и write-path; `GoogleAppsScriptService` оставить для read/download из файла. Модель и таблицу удалить отдельным contract-шагом после резервирования данных. Обновить ссылки на экран редактора в инструкции.

## 9. Миграция и обратная совместимость

1. Снять резервную копию БД, `script_assets` и конфигурации, необходимой для расшифровки. Перед изменениями выполнить baseline-проверки, отдельно зафиксировать результаты и ограничения среды.
2. Добавить nullable-схему и новые таблицы. Data backfill выполнять отдельными идемпотентными командами с dry-run и отчётом, не seeding внутри миграций.
3. Перенести эффективные URL и токены в connections. Дедуплицировать только при полном совпадении нормализованного URL и секрета; одинакового URL недостаточно. Не выводить секреты или их fingerprints в отчёт. Неполные настройки вынести в список ручного исправления.
4. Перенести эффективные fallback-маппинги и default-значения в интеграции; сверить маршрутизацию на том же наборе входных данных до/после. Назначить доступы явно; не давать всем пользователям все интеграции автоматически.
5. Выдать индивидуальные токены и обновить Script Properties каждой таблицы. До её перевода сохранять управляемый legacy-доступ. Хранить явный признак готовности интеграции к UUID-only режиму.
6. UUID назначается в Sheets. Первая привязка к существующему экспорту выполняется в контролируемом режиме миграции при остановленной синхронизации/перестановке строк и подтверждении task ID из существующей ссылки. Не сопоставлять только по текущему номеру строки. Неоднозначные случаи и строки без достаточных данных блокировать для ручной сверки; не создавать новые задачи автоматически.
7. После привязки идентифицировать только по UUID. Новый UUID не должен захватывать старую запись по совпавшему row number. Для legacy-запроса к уже мигрировавшей неоднозначной позиции возвращать conflict с инструкцией обновить скрипт.
8. Снять глобальный unique с `external_id` только после перевода алгоритма поиска. Сохранить формат поля и индекс. Проверить возможность повторного использования позиции другой записью и доступность legacy-истории.
9. Восстановить историю известных состояний без выдумывания старых попыток: существующий экспорт — снимок, а не полный журнал. Неизвестные результаты и failed с task ID классифицировать явно.
10. Переключить read-path на новую схему, проверить данные и права, затем удалить fallback, старые поля и `script_assets` отдельными contract-миграциями после переходного периода.

Для каждого этапа описать откат кода и схемы. После появления UUID-связей нельзя откатываться на старый алгоритм row number без остановки записи и отдельной процедуры восстановления. Destructive down не считать достаточным rollback. Удаление старых endpoints допустимо только при подтверждённом отсутствии их потребителей и отдельном согласованном релизе.

## 11. Проверки и критерии приёмки

- [ ] Создание новой строки даёт одну AC-задачу и подтверждённую связь; повтор неизменённых данных даёт skip без PUT.
- [ ] Ошибка update не разрешает создание второй задачи через sync или legacy create.
- [ ] Одинаковые task ID в разных connections/projects не смешивают состояние; несовпадение task ID и source record блокируется до HTTP.
- [ ] Два независимых процесса на MariaDB для одной записи выполняют не более одного внешнего create; проверить также гонку первого insert, а не только обновление существующей записи.
- [ ] Timeout после внешнего create, некорректный успешный ответ и ошибка записи в БД сохраняют unknown/возможность восстановления без автоматического второго create.
- [ ] Истёкший lease и поздний ответ не перезаписывают чужую операцию и не запускают повторное создание.
- [ ] Удалённая AC-задача не воссоздаётся автоматически; ручное восстановление проверяет назначение и фиксируется в аудите.
- [ ] Сортировка полной строки, вставка строк, повторное использование номера и запись ответа после перемещения сохраняют правильную UUID-связь.
- [ ] Копирование UUID блокируется; явная новая запись получает новый UUID без изменения исходной связи.
- [ ] Миграция существующей связи не создаёт AC-задачу; неоднозначное сопоставление останавливается с отчётом.
- [ ] SHA-256 различает поля с `|`, учитывает маппинги, null/очистку назначений и итоговый payload; hash не меняется из-за случайного порядка JSON-ключей.
- [ ] Новое API сохраняет единый контракт, legacy — прежние успешные ответы и известный duplicate conflict; исправленные небезопасные случаи документированы.
- [ ] Токен одной интеграции не обращается к другой; отключение, отзыв и ротация проверены; глобальный токен не принимается новым API.
- [ ] Manager/viewer не видят чужие карточки, статистику, историю, справочники и действия при прямом запросе URL; viewer не выполняет mutations.
- [ ] Секреты отсутствуют в сериализации, истории, логах, исключениях, error responses и audit before/after; проверить внешний ответ, содержащий отражённый токен.
- [ ] Обычное сохранение настроек и проверка connection не создают Task List и другие внешние сущности.
- [ ] Backfill повторяем, имеет dry-run, сохраняет исторические записи и не объединяет разные credentials одного host.
- [ ] Скачиваемый скрипт совпадает с файлом текущего деплоя; DB-версии экспортированы до удаления.
- [ ] Инструкция описывает чистую установку, перевод действующей таблицы, права, ротацию и восстановление unknown.
- [ ] Выполнен этап обновления версий (§13): зафиксированы исходные/целевые версии, совместимость и результаты аудитов; установка из lock-файлов и `make check` проходят в обновлённом окружении.

Проверки: focused PHPUnit для изменённых компонентов; feature-тесты API и Orchid actions; отдельная проверка реальной конкуренции на MariaDB (SQLite in-memory недостаточно); воспроизводимые проверки Apps Script с зафиксированными шагами сортировки/копирования/конкурентного запуска. Автоматизировать JS-проверки при доступном подходящем harness, не изображать ручные проверки выполненными.

В конце этапа выполнить релевантные Pint/PHPStan/тесты; перед PR — `make test`, перед итоговым завершением — `make check` (включает frontend build). Указать реальные результаты, команды, ограничения окружения и непроверенные интеграционные сценарии. Не обращаться к рабочему ActiveCollab и не менять реальные Google-таблицы в автоматических тестах.

Откат кода и lock-файлов выполнять согласованно с окружением; для MariaDB использовать проверенное восстановление резервной копии, не обещать безопасный downgrade существующего data volume.
