Общий результат — безопасная многопользовательская синхронизация Sheets → ActiveCollab и обновлённый поддерживаемый стек. ТЗ требует отдельных согласований этапов. ## Scope

Ближайшая реализация 1.1:

- Запретить повторный create при наличии task ID независимо от последнего `status`, включая ошибку update.
- Разрешать legacy update только при совпадении интеграции, проекта, исходной записи и task ID; исключить поиск по одному глобальному task ID и fallback на произвольную запись.
- Сохранять подтверждённые task ID/URL, hash и payload при ошибке update; закрепить это регрессиями.
- Возвращать безопасный конфликт для отсутствующей, чужой или неполной привязки до любого внешнего HTTP-запроса.

В этом шаге не менять схему БД, формат `external_id`, MD5, успешные legacy-ответы, Apps Script, токены, настройки интеграций или зависимости. Атомарность и unknown не решены шагом 1.1: публикацию как полностью безопасной синхронизации отложить до оставшихся частей P0. Изоляция запросов по токену появляется на этапах 2/4; scoped lookup не заменяет авторизацию.

## Implementation Plan

1. Зафиксировать исходное состояние: повторно прочитать документы и `git status`, выполнить `make test`, `make lint`, `make analyse`. Сохранить реальные результаты и ошибки окружения; не приписывать старые результаты текущему запуску.
2. В API tests добавить воспроизводимые регрессии: успешная связанная запись → ошибка update → create получает прежний 409 с исходными task ID/URL, без POST; update без экспорта, с чужим external ID, интеграцией, проектом или task ID получает 409 и `Http::assertNothingSent()`. Добавить случай совпадающих task ID в двух интеграциях: обновляется только точная привязка. Сначала убедиться, что тесты воспроизводят существующую ошибку.
3. В repository заменить глобальный `findByTaskId(int)` на поиск с обязательным integration/project/external ID/task ID. Для create сначала получить запись по locator и проверить её контекст: нельзя считать запись с `integration_id = null` или другим project ID новой, иначе возникнет повторный create либо unique violation. Не подхватывать чужую запись и не исправлять исторические данные автоматически. Добавить repository tests по каждому ограничению.
4. В сервисе create блокировать создание по наличию task ID, а не только по `status`. Полная подтверждённая связь в правильном контексте возвращает существующий `TaskAlreadyExistsException`; task ID без URL либо `created/updated` без полной связи возвращает новый binding conflict без HTTP. Запись правильного контекста без привязки сохраняет прежний путь; безопасность повторов pending/unknown будет изменена в 1.2–1.3.
5. В update требовать полную совпадающую привязку до построения payload и HTTP. Удалить fallback `findByExternalId()` после неудачного поиска task ID. После проверки экспорт всегда существует: убрать условные ветви, допускающие update без экспорта. Ошибка маппинга или HTTP оставляет task ID/URL, последний успешный hash и подтверждённые source/AC payload/response неизменными; `status/error_message` отражают текущую legacy-ошибку.
6. Добавить `TaskBindingConflictException` и renderer: HTTP 409, `message` с фиксированным текстом, `error.code = legacy_binding_conflict`, `error.operation_id = null`, `error.retryable = false`. Не возвращать метаданные несовпавшей записи. Duplicate create по корректной полной привязке сохраняет прежние `message` и `data.task_id/task_url` без изменения. Общий новый error envelope и обработка upstream появятся в 1.3/2.
7. Обновить API/logic docs по фактическому поведению; выполнить проверки ниже. Отдельно перечислить нерешённые concurrency/unknown/UUID/auth риски, чтобы результат 1.1 не воспринимался как готовность всего этапа 1.

## Risks

- 1.1 не устраняет гонку create и не различает failed/unknown. Повторы pending остаются прежними до 1.2–1.3. Не заявлять гарантии отсутствия дублей при конкурентной отправке или таймауте.
- Legacy global token по-прежнему общий; изоляцию по пользователям/индивидуальным токенам реализуют следующие этапы.
- Исторические записи с null integration ID, несогласованным проектом или неполной связью начнут получать conflict. Это намеренная остановка небезопасного обновления; исправлять их отдельным backfill с dry-run и отчётом.
- Изменение project/base URL существующей интеграции пока не заблокировано во всех административных путях. Проверка project ID защищает от части ошибок, но полную неизменность назначения обеспечит этап 3.
- Raw upstream errors и секреты в них — известная проблема следующего шага 1.3; не добавлять новых путей раскрытия в 1.1 и не заявлять полное исправление логирования.
- SQLite покрывает только последовательные проверки 1.1. Конкуренцию проверять в 1.2 двумя независимыми процессами на выделенной MariaDB; существующий `phpunit.xml` использует SQLite in-memory.
- Для этапа 7 не подтверждены latest, поддержка и аудит; номера целевых версий нельзя выбирать по памяти. Несовместимость Laravel/Orchid/PHP и upgrade MariaDB могут потребовать отдельной последовательности и восстановления из backup.

Для 1.1 backfill и миграций нет. Откат — вернуть согласованные изменения кода/документации, данные не удалять; возврат старого кода снова открывает уязвимый update/create и требует остановки синхронизации. Для 1.2–1.4 составить отдельную процедуру backup/backfill/rollback; после UUID-перехода возврат к row number без остановки записи недопустим.
