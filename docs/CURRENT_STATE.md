# Текущее состояние проекта

Документ фиксирует фактическое устройство проекта, состояние проверок качества и
известные технические ограничения на 28 июля 2026 года. Подробные контракты и
инструкции остаются в тематических документах из раздела
[«Связанная документация»](#связанная-документация).

## 1. Назначение

SheetCollab синхронизирует задачи из Google Sheets с ActiveCollab:

```text
Google Sheets
    → Google Apps Script
    → Laravel API
    → ActiveCollab API
    → журнал синхронизации в Laravel
    → ссылка на задачу в Google Sheets
```

Практический сценарий:

1. QA или менеджер заполняет строку в Google Sheets.
2. Пользователь выбирает в меню Apps Script создание или обновление задачи.
3. Apps Script читает строку и отправляет JSON в Laravel с Bearer-токеном.
4. Laravel находит активную интеграцию по `spreadsheet_id`.
5. Сервис применяет маппинги и формирует название и HTML-тело задачи.
6. Единственный HTTP-репозиторий выполняет запрос в ActiveCollab.
7. Laravel сохраняет состояние и ответ ActiveCollab в журнале экспортов.
8. Apps Script записывает ссылку или сообщение об ошибке в таблицу.

## 3. Карта компонентов

### Клиент Google Sheets

- `resources/apps-script/activecollab_sync.gs` — исходный шаблон Apps Script;
- скрипт находит заголовки в первых 10 строках;
- обязательные поля: `Стенд`, `Раздел`, `Описание проблемы`;
- Laravel URL и интеграционный токен читаются из Script Properties;
- ActiveCollab API token в скрипт не передаётся;
- каноническая редактируемая версия скрипта хранится в таблице
  `script_assets`, а файл используется для первоначального заполнения.

### HTTP-слой

- `routes/api.php` — пять endpoint-ов интеграции;
- `VerifyIntegrationToken` — проверка общего Bearer-токена;
- `StoreActiveCollabTaskRequest` и `UpdateActiveCollabTaskRequest` — валидация;
- `ActiveCollabTaskController` — преобразование запроса в DTO и вызов сервисов;
- `bootstrap/app.php` — JSON-обработка `404` и `409`.

### Бизнес-логика

- `ActiveCollabTaskService` — оркестрация create/update и статусов экспорта;
- `ActiveCollabTaskBodyBuilder` — название и безопасное HTML-тело;
- `ActiveCollabMappingService` — task list, assignee и label;
- `ActiveCollabIntegrationSettingsService` — нормализация настроек,
  поиск или создание task list;
- `ActiveCollabTaskData` — readonly DTO входных данных.

### Данные и внешние запросы

- `ActiveCollabRepository` — единственная точка HTTP-вызовов ActiveCollab;
- `ActiveCollabIntegrationRepository` — поиск активной интеграции;
- `ActiveCollabExportRepository` — журнал синхронизации;
- `ActiveCollabIntegration` — настройки одной Google Sheets таблицы;
- `ActiveCollabTaskExport` — текущее состояние синхронизации строки;
- `ScriptAsset` — канонический Apps Script в базе данных.

### Orchid

Админка позволяет:

- создавать, редактировать и отключать интеграции;
- задавать project, task list и API token;
- настраивать маппинги task type, assignee и label;
- просматривать журнал экспортов;
- редактировать и скачивать Apps Script;
- управлять пользователями и ролями.

## 4. Идентификация и состояния синхронизации

Одна строка таблицы идентифицируется значением:

```text
external_id = {spreadsheet_id}:{sheet_id}:{row_number}
```

Поле `external_id` уникально в `active_collab_task_exports`. При повторном
create для записи со статусом `created` или `updated` API отвечает `409` и
возвращает существующие `task_id` и `task_url`.

Используемые состояния:

```text
create: pending → created | failed
update: created | updated → updated | failed
```

При успешной операции сохраняются исходный payload, payload ActiveCollab,
ответ ActiveCollab, ссылка, ID задачи и `sync_hash`.

`sync_hash` — MD5 от 13 полей содержимого строки. Сейчас он хранится для
аудита; пропуск update при неизменившихся данных не реализован.

## 5. Авторизация и секреты

- Все `/api/integrations/activecollab/*` защищены
  `GOOGLE_SHEETS_INTEGRATION_TOKEN`.
- Для каждой интеграции можно хранить отдельный ActiveCollab API token.
- Токен интеграции шифруется стандартным encrypted cast Eloquent.
- Helper-endpoints `task-lists`, `users` и `labels` используют глобальную
  конфигурацию ActiveCollab, а не интеграцию конкретной таблицы.
- ActiveCollab token не должен попадать в Apps Script, API-ответы и логи.
- Смена `APP_KEY` делает ранее сохранённые зашифрованные токены нечитаемыми.

Локальный seeder создаёт `admin@example.test` с фиксированным паролем
`LocalAdmin123!`. Seeder предназначен только для локальной среды. В любом
другом окружении учётную запись необходимо заменить или отключить.

## 7. Известные ограничения и риски

### 7.1. Повторный create после failed

Защита от дубликатов применяется только к статусам `created` и `updated`.
После ошибки update запись становится `failed`, поэтому прямой повторный
`POST /tasks` для той же строки может создать вторую задачу в ActiveCollab.
Штатный Apps Script снижает вероятность этого, поскольку при наличии ссылки
предлагает update, но сервер сам такой сценарий не запрещает.

### 7.2. Поиск журнала update только по task ID

При update журнал сначала ищется по глобальному `task_id`, без ограничения по
`integration_id` или проекту. В разных экземплярах ActiveCollab одинаковые
числовые ID возможны. Тогда может быть обновлена запись журнала другой
интеграции, хотя внешний запрос уйдёт в интеграцию из текущего
`spreadsheet_id`.

### 7.3. Update без записи истории

Если журнал не найден ни по `task_id`, ни по `external_id`, Laravel всё равно
обновляет задачу в ActiveCollab, но новую запись `active_collab_task_exports`
не создаёт. Такое обновление не будет видно в истории Orchid.

### 7.4. Конкурентные create-запросы

Проверка существующего экспорта и создание `pending` не объединены в
транзакционную или атомарную операцию. Два одновременных запроса для одной
строки могут столкнуться на уникальном индексе `external_id`; проигравший
запрос получит ошибку БД вместо ожидаемого `409`.

### 7.5. Расхождение fallback-маппингов

Актуальная реализация `ActiveCollabMappingService` читает маппинги из модели
интеграции. Fallback к массивам `services.active_collab.task_lists`,
`assignees` и `labels` фактически не применяется, хотя такие массивы
присутствуют в конфигурации и упоминаются в части старой документации.

### 7.6. Устойчивость внешних запросов

Для ActiveCollab HTTP-клиента не настроены явные retry и timeout. Временный
сетевой сбой сразу завершает операцию ошибкой и переводит существующую запись
экспорта в `failed`.

### 7.7. Связи базы данных

`active_collab_task_exports.integration_id` индексирован, но не имеет внешнего
ключа. Удаление интеграции оставляет историю с её UUID, однако Eloquent-связь
`integration` после этого возвращает `null`. Это сохраняет аудит, но
целостность обеспечивается только приложением.

### 7.8. Непроверяемые клиентские сценарии

Логика Apps Script зависит от заголовков и поведения Google Sheets API, но не
покрыта автоматическими тестами. Изменения названий колонок, RichText-ссылок и
Script Properties необходимо проверять вручную в тестовой таблице.

## 8. Рекомендуемый порядок дальнейшей работы

1. Зафиксировать серверные правила повторной синхронизации после `failed`.
2. Ограничить поиск export при update интеграцией и внешним идентификатором.
3. Всегда создавать или обновлять запись истории при успешном update.
4. Сделать регистрацию `pending` атомарной и возвращать предсказуемый `409`.
5. Синхронизировать контракт fallback-маппингов между кодом и документацией.
6. Добавить retry/timeout с осторожной политикой повторов для create.
7. Добавить тесты Orchid-операций и тестируемый слой для Apps Script.
